# 005 — Targeted household gaming observation — spec r2 + r3 access amendment

Status: **approved for B1 offline implementation** · 2026-10-24. This replaces r1 entirely. The existing directory is retained for stable links; its historical `continuous-household-reporting` slug does not define the new scope. Approval scope is recorded below.

## Outcome and governing sources

An owner starts a prospective 3-, 4- or 5-day household observation campaign. Available DNS evidence is captured without an open browser. Anyone on the intended LAN can generate and read a frozen gaming-signal report during or after the campaign, with explicit missing coverage. Capture ends at the recorded deadline. This is a household observation tool, not proof that a person played or has gaming disorder.

## Actors and scope

- **Owner:** starts/finishes/extends a campaign within its five-day cap, reviews namespace rules, manages retention and publication, and uses protected diagnostics. One active campaign at a time.
- **LAN viewer:** reads shared gaming summaries, requests bounded local report generation and exports that same projection. Cannot start, extend or reconfigure capture or dispatch external research.
- **Operator:** installs and supervises the host bridge/application using documented Make flows, checks recovery and manages private backups under separate live-operation authorization.

Include campaign lifecycle, bounded read-only extraction/import, honest empty/gap states, full-campaign/day reports, reviewed rules, LAN access separation, Docker/Make delivery, restart recovery and retention controls. AI is disabled in the 005 deployment profile; existing saved eligible classifications may be read with their evidence labels.

Exclude continuous presence, device/person attribution, endpoint agents, interception, router changes, blocking, alerts, automatic suspicion detection, diagnoses, relapse/recovery scores, clinical questionnaires or recruitment, React rewrite and provider-policy repair. DNS continuity, shutdown safety and failover are outside scope under the owner's Starlink backup-DNS assumption. Bypassed DNS remains an observation limitation. This feature neither verifies nor manages that backup.

## Decision defaults and deployment prerequisites

These are concrete draft choices for combined review, not inferred user approval:

- Collection chunks: up to one hour; initial settling grace 120 seconds, validated against persisted-source behavior before live use. First reports may wait for a closed chunk. This is not a real-time detector.
- One active campaign, one collection job, one report build; campaign duration is elapsed UTC hours (72/96/120), with local dates only for display/day filtering.
- Finalization has a 24-hour recovery allowance after the recorded end. Reads during that allowance still cover only the campaign. On expiry finalize with gaps; later repair is an explicit owner operation, never automatic renewed monitoring.
- Require a retention choice of 1–30 days after completion, with 7 days suggested. Expiry hides the shared report; private copies persist until explicit retirement. Document this distinction before start.
- Before deployment the owner must confirm the intended LAN audience/address and TLS trust, private storage/retention choice, namespace baseline and service-account/boot setup. An actual resource budget is measured, not assumed from proposed VM sizing. These do not block drafting or offline implementation.

## R3 access amendment — approved for offline B5A

The owner requested that every reachable LAN browser have the full existing web interface and its actions without signing in, using a simple local IP over HTTP without per-device certificates (conversation following acceptance of B3/B4/B5 offline work, 2026-10-25). The r2 approval remains valid for delivered offline work. This approved amendment replaces the conflicting r2 actors/permissions, A10–A11 and HTTPS/TLS prerequisite only for the opt-in 005 LAN profile; all other r2 requirements remain in force. Project-wide MVP §4/§7's protected-owner/TLS baseline is superseded for this initial-stage profile only.

- Anyone who can reach the one approved VM IP and port on the household LAN may open all **existing browser pages, API views, exports and web actions** without an account, including dashboard, diagnostics, inventory editing, gaming, analysis views and campaign start/extend/finish. This is LAN-wide shared control, not an owner identity or device-based authorization. No new raw-data or retirement browser route is implied; retirement, backup, installation and source/host administration remain explicit host/operator operations. AI and provider dispatch remain disabled in the campaign profile, including direct requests. Do not expose credential files, provider keys, the Docker socket or a source database mount to the web container.
- The opt-in campaign origin is a single explicit `http://<approved-private-VM-IP>:<port>` with exactly that Host. The proposed default is `http://10.10.10.20:8787`, subject to a successful second-device reachability check; VM and household client subnets differ. No domain, browser certificate warning, sign-in, WAN publication or automatic router/Proxmox change is part of this change. The original authenticated HTTPS loopback profile remains unchanged.
- LAN reachability **does not** guarantee that only intended household members can access the service. Guests, compromised LAN devices and any network path to that VM IP can read the existing household web views and perform its actions. HTTP provides neither encryption nor server authentication; observed domains, client identifiers and action requests can be exposed or altered on that network. State these risks plainly before live publication; never claim this is a secure private audience or a suitable clinical/participant deployment.
- Preserve request-size bounds, exact Host and Origin checks, same-origin/fetch-metadata restrictions, bounded queues/rates, path validation, AI-off enforcement and a browser confirmation for destructive or deadline-changing actions. Anonymous state-changing requests must not become drive-by cross-site requests merely because sessions disappear. The app must render working action forms without owner session/CSRF dependency in this profile. Do not silently allow cross-origin access or arbitrary work commands.
- **Revised acceptance (r3 proposal):** (1) On a second device that can actually route to the VM, typing the HTTP IP:port opens all existing pages and permitted actions without a login, certificate installation or warning; direct URLs and exports behave consistently. (2) A campaign start/extend/finish and an inventory edit work through the browser after intentional confirmation, while hostile Host/Origin/cross-site or oversized requests fail; AI/provider calls remain zero. (3) Loopback r2 login/TLS and owner-only routes remain protected when the opt-in LAN profile is off. (4) Documentation names precisely which existing web views reveal raw activity, and which host-only actions still need the operator; no network changes or live checks are inferred from offline tests.
