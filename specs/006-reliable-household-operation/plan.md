## D1 — Configuration and credentials

Use one versioned, strict JSON operator document, explicitly selected by `CONFIG=/absolute/path/operator.json` (default path documented and printed as a safe logical location, never auto-discovered). Fresh example lives in the repo, private document outside it, 0600 under 0700. JSON avoids introducing a parser dependency or conflating Docker dotenv semantics with operator settings. It contains nested network, paths, release, bridge, reporting and AI sections. Credentials are references `{file, format, variable}`; supported formats are `bare` and `dotenv`, explicit regardless of basename. AI-disabled ignores optional credential references and never reads/mounts them.

Reject duplicate JSON keys, unknown fields and invalid types/ranges. Precedence: explicit CONFIG selects one file; schema defaults fill optional omissions; supported command arguments identify an operation/release/campaign, never silently override operator settings. Reject legacy environment/Make settings that conflict with the selected config, including ambient Compose variables. No `source`, `eval`, shell substitution or Make include of private files. Invoke subprocesses with argument arrays and an allowlisted environment. Generate a private, resolved Compose document (no unresolved interpolation) and explicit empty interpolation env file; neutralize ambient `COMPOSE_*` and application variables. Test from arbitrary working directories containing hostile `.env` files. Generated artifacts record configuration schema and non-secret fingerprint; commands verify them before use.

One credential parser for provider and Exa: blank/comment lines plus `NAME=value`, single-quoted or double-quoted literal values. No interpolation, escapes, multiline values, command substitutions, export prefixes or inline comments. Permit printable literal key punctuation; reject whitespace/control characters inside the resulting key. Strip only matched outer quotes. Reject duplicate keys even if equal, missing explicit variable, empty value and multiple competing credential sources. Error reports key/line/reason, never content. Ownership/mode/symlink checks precede opening; mount only selected credential files read-only into owner container with matching non-root UID. Shared app mounts none. Redaction tests cover exceptions, process arguments, Compose diagnostics, HTTP, logs and image contexts.

Migration is explicit preview then apply, leaving old files intact. Read named legacy settings, Compose selections and bridge JSON without shell evaluation; require owner resolution of conflicts rather than guessing. Preserve paths, identity, passwords, sessions, TLS, evidence and ledger. Produce private new config referencing existing bare Exa and dotenv provider files; optional normalized credentials copy is separate and never overwrites originals. Capture pre-migration config/release manifest. Harden owned file modes only during authorized migration. Legacy commands initially delegate to the new driver with deprecation guidance; contradictory mixed paths fail. No claim that bare `docker compose` automatically loads the operator document.

## D2 — Releases, host runtime and commands

Keep local builds as the default distribution strategy. Build from a clean selected commit and locked dependencies; produce a versioned tag, local immutable image ID, OCI source/revision/version labels, lock/base-image hashes, host-package hash and schema compatibility manifest. Tags are labels, not identity. Resolve both deployments to the same recorded image ID; imported image archives require matching checksums/IDs. Optional `docker save/load` bundle supports another host without a registry. Publishing to any registry requires separate authorization. Preserve the preceding release bundle for rollback.

Package host bridge/export tools and their locked Python environment in a versioned private release directory during explicit setup/build, not at service startup. Verify Python/platform dependencies and installed package hashes. Retain the host bridge/Docker CLI architecture and non-root system unit; Docker membership remains privileged in practice. No web Docker socket or resolver mount. Release switching changes the selected host tool bundle and both containers together. System interpreter/uv provisioning is a documented prerequisite; downloads occur only in explicit build/preparation with appropriate authorization.

Sanitized status compares selected release, actual IDs/labels, host bundle hash, rendered config fingerprint and schema. Development working-tree drift is reported separately; it does not pretend mounted immutable images follow source edits. Start and campaign-start refuse unknown/mixed releases. Upgrade stops bridge and both writers, creates a verified backup, migrates once, recreates both from the selected ID, checks both before restoring operation. Failure leaves both stopped or restores the prior compatible pair; never presents one old/one new instance as success. Use a maintenance lock/journal to make interrupted stages resumable. Prefer brief explicit downtime to a rolling mixed-version deployment.

Proposed public command surface (thin Make wrappers over one typed operator driver):

| Command | Effect and boundary |
|---|---|
| `make stack-setup CONFIG=...` | Validate, prepare private non-root paths/release artifacts and render owner-run unit/network scripts; no install, publication, capture or research. Explicit build option may fetch locked dependencies. |
| `make stack-check CONFIG=...` | Offline validation by default; explicit `MODE=live` reads narrow local runtime metadata/source readiness only, without capture or paid APIs. |
| `make stack-start CONFIG=...` | Start selected application pair only after prepared guards and release checks; resume previously authorized bridge work only when explicitly requested. No new campaign. |

| `make stack-backup ARCHIVE=...` / `stack-restore ARCHIVE=... DEST=...` | Verify consistent archive; restore defaults to isolation. Production promotion is a separate explicit operation. |
| `make stack-uninstall` | Preview and explicitly remove owned app/bridge publication/services only; retain evidence/config/images/backups and DNS. |

Research remains protected preview/confirmation. Owner runs rendered privileged preparation separately. A generic “up” never performs network changes, starts a campaign or spends money.

Pinned dependency maintenance: monthly review and prompt review of applicable security advisories, explicit lock/base/Pi-hole digest change, changelog and compatibility review, O/P gates, then separately authorized deployment. ## D3 — Network policy and failure boundaries

One versioned network section generates both helpers, Compose bindings and verification expectations. Proposed approved path: LAN `192.168.1.0/24` enters Proxmox `wlo1`, destination `192.168.1.10`, TCP 8787/8789; DNAT to VM `10.10.10.20` on matching port, VM ingress `ens18`. Bind both published ports only to that VM address; shared HTTP origin exactly `http://192.168.1.10:8787`, owner HTTPS origin exactly `https://192.168.1.10:8789`. Owner TLS SAN/trust must match. Keep distinct stable IPv4-only application bridges; no wildcard binds, extra VM/loopback origins or IPv6 publication. Healthchecks run inside containers. Any diagnostic bypass must be separately documented/approved, never default.

Retain owned 8787 relay table/unit; add separately owned 8789 relay table/unit so removing owner publication does not remove shared publication. Shared manifest/renderer prevents duplicated handwritten constants. Adopt the historical operational 8789 rule only after exact ownership/diff review and private backup; unknown tables/rules abort. Both VM guards and Proxmox dashboard forwarding guards derive from the same manifest. Proxmox forwarding rules require allowed ingress/source AND original destination/port matching the approved relay; deny direct forwarded VM app-port and application-subnet access outside those paths. VM guards restrict ingress/source and direct Docker bridge paths for both apps. Scope all drops narrowly to dashboard addresses/networks; leave DNS/8443, routes and unrelated forwarding untouched.

DNAT alone is not access control. At the VM, a forwarded LAN source may look identical whether it originally targeted Proxmox or the VM; therefore the Proxmox forwarding/original-destination check is necessary. Host headers only constrain HTTP, and remain forgeable. Verify Docker firewall backend, hook ordering, conntrack tuple behavior, bridge addresses and anti-spoofing assumptions before live apply. Fail closed if those preconditions cannot be established. Privileged VM/Proxmox administrators are trusted; this design does not isolate against host root or compromised LAN hosts impersonating allowed sources. Owner authentication protects research even on the allowed LAN. If packet-path tests invalidate this design, return the affected network design for review rather than introducing a proxy/topology change silently.

Helpers validate syntax/topology/ownership/listener conflicts on both ports before mutation; private backup, atomic owned-table transactions and journaled unit installation allow safe reruns. Never flush the ruleset. Guard installation precedes publication, and systemd ordering reapplies guards before Docker exposes ports after reboot. Reapply/reload/install are idempotent and check postconditions. Partial failure keeps publication stopped and preserves last known policy; do not delete guards on failure. Rollback per relay restores only its owned table/unit; guard rollback refuses while either protected service is exposed. DNS relay rollback is independent. Intentional application uninstall first stops publication, then owner can remove dashboard-only policies.

Positive tests: intended second-device HTTP shared view and authenticated TLS owner view. Negative tests: wrong source subnet/interface, forged Host to direct VM address, direct container address, IPv6, alternate host IP, owner unauthenticated/cross-origin mutations and shared AI POST. Packet denial and HTTP rejection are recorded separately. Compare DNS UDP/TCP 53 and admin 8443 before/after apply/reinstall/rollback/reboot. These are live gates, not claims established here.

## D4 — Collector correctness and visible status

First-time registration requires explicit setup action; changed resolver generation requires owner continuity review and a new generation record, never relabelling historical rows. Persist sanitized bridge heartbeat/outcome independently of successful worker calls, in an atomically replaced private status file readable by the apps. Include attempt start/end, code, stage, consecutive failures and last successful bridge/capture/import timestamps, no source names/identity string. Apps derive stale heartbeat themselves; CLI additionally reads systemd state. UI reports timer state unavailable when no fresh host status exists. DB records remain canonical for successful imports/coverage. Capture failure must not erase prior success. Missing/unwritable status is visible as unavailable, not healthy.

Keep 60-second scheduling, at most 10 chunks/600 seconds per tick, 610-second service timeout, ≤3600-second windows, 120-second settling and one reconciliation pass at the existing 600-second allowance. Max three capture attempts per chunk, within the existing 24-hour finalization allowance; retry only transient failures with bounded delay. Identity/config failures latch until configuration fingerprint changes or an explicit local retry-check succeeds. They do not repeatedly read FTL. Heartbeat is stale after 720 seconds (allows one bounded running tick plus scheduling); overdue eligible capture/import is stale after 15 minutes beyond eligibility while a campaign is active. Show a running-tick state separately. Tests use a fake clock. No active campaign performs no capture; completed old data is labelled historical. Waiting for the next closed window is not stale until work is due.

Report status includes requested/covered bounds, latest selected import and evidence revision; newer saved evidence produces “update available.” Successful-empty requires an acknowledged successful capture envelope and its retention context; missing/error/unknown continuity cannot become empty. Restart uses durable pending jobs, leases and retained source bounds; timer persistence alone is not catch-up. Preserve query identity, deduplication and gap semantics.
