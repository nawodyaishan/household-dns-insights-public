# 006 — Reliable household operation and understandable gaming reports

Revision r1 · 2026-11-01 · Planning only. Implementation and live execution have not begun.

## Outcome and authority

The owner can configure, check, operate and recover the existing Pi-hole-to-report stack through one documented configuration entry point and a small command set. Both dashboards use one selected application release. Collection failures are visible independently of web health. A simple period-based gaming-related DNS report explains associations, evidence and missing coverage. Optional owner research progresses through a bounded selection without paying repeatedly for unchanged unresolved names.

This is one operational outcome with independently reviewable batches, not a replacement stack. Governing sources are [MVP §§2–7 and 9](../../docs/project-scope/mvp-spec-v1.md), [005 spec and acceptance](../005-continuous-household-reporting/spec.md#combined-approval), [005 tasks](../005-continuous-household-reporting/tasks.md), [004](../004-gaming-web-view/spec.md), [bring-up runbook](../../docs/operations/household-bringup-runbook.md) and [campaign runbook](../../docs/operations/005-campaign-runbook.md). Historical architecture and handovers are evidence, not current execution authority. The verified baseline and discrepancies are in [plan](plan.md#verified-baseline).

The owner's “005 b5c approved” acceptance remains valid. It accepts the delivered separate owner TLS dashboard and bounded paid run, without authorizing new work or spending. This feature deliberately retains shared AI-off HTTP access and protected owner TLS research. Simplifying navigation does not revoke existing shared-control actions or silently consolidate authentication.

## Scope and exclusions

Include reproducible dashboard publication, collector identity/readiness and durable failure status, recovery, configuration and credential consistency, immutable application releases, operational commands, coherent gaming report periods/revisions, and bounded optional research. Reuse Python/FastAPI/Jinja, SQLite, Docker Compose, systemd and the host bridge. No verified limitation requires another framework, database, orchestrator, secret service or collection architecture.

Exclude automatic household routing/Starlink changes, endpoint agents, interception, continuous presence, notification services, clinical claims, gameplay detection guarantees, registry publication, automatic dependency updates, automatic paid research and deletion of private evidence. Root firewall execution and household DNS changes remain owner interventions. Stopping campaigns or application services does not stop Pi-hole logging; resolver expiry does not remove imported evidence, frozen reports or backups.

### Reporting truth contract

Every report states household DNS observations, with device/player attribution unknown on the router-forwarded path. Query counts are not matches, players, connections or intensity; first/last lookup times are not session boundaries or duration. Missing signals or quiet periods do not prove no gaming. DNS records do not prove application contact or gameplay. AI labels observed destinations from evidence; it does not discover traffic or infer household behavior. A purpose labelled gameplay/matchmaking-related describes a destination, not a household event.

### Fully complete

All R01–R18 have their required O/P evidence and no unresolved critical defect; L checks establish the approved network paths, DNS coexistence, freshness, restart/reboot persistence and one new **72-hour** campaign through its actual deadline and finalization. A five-day synthetic test validates bounds/recovery, not five-day household operation. Claim only the live duration actually observed. The accepted 18.591-hour campaign is historical evidence, not this three-day gate. H is the owner's acceptance of results and report comprehension. If live work is deferred, mark implementation complete / operational acceptance pending, never fully complete. Optional AI can be fully implemented using fake adapters; a real paid run is not required for this feature's completion and must remain explicitly unvalidated if not authorized.

## Dependencies, risks and decisions

Requires owner-controlled Docker/systemd hosts, the existing retained source, private disk capacity and preserved source-generation continuity. No new consent is inferred for collection. Main risks: network bypass through routed VM/container paths; cross-instance SQLite writers during migration; irrecoverable source expiry; credential leakage; mutable model pricing; and ambiguous DNS interpretation. Mitigations and measurable gates are in the plan/tasks.

No owner answer blocks drafting or offline implementation after approval. Proposed defaults are reviewable here: two profiles retained, local release distribution, three-day live acceptance and AI disabled on fresh setup. Before live execution, the owner must approve exact network policy/interfaces, maintenance and recovery windows, campaign duration/retention and any separately requested spend ceiling. Missing live decisions block only their dependent execution.
